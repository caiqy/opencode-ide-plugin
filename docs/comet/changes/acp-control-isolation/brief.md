# 目标

彻底优化 ACP（Agent Client Protocol）与 MCP（Model Context Protocol）在 WebGUI 状态面板中的控制粒度与交互体验：实现默认全量禁用（最小权限原则）、解除大类/Server 对子工具操作的强绑定、支持大类/Server 关闭下直接勾选子工具并智能级联激活对应宿主/服务、支持一键全部启用/全部禁用；彻底解决 VS Code 与 IntelliJ IDEA 双端在同一个项目中配置 `opencode.json` 可能导致的配置冲突与覆盖问题，在前端和后端引入宿主平台命名空间隔离（`acp.platform_vscode` / `acp.platform_intellij`），并向下兼容旧版扁平结构。

# 范围

- **默认全量禁用（安全优先、最小权限）**：
  - 在 `packages/opencode/webgui` 与核心层中，未显式在配置中开启的 ACP 大类及子工具默认值统一改为 `false`；
  - 新项目或未配置环境下，所有能力卡片展示为 `0/N 启用`，大模型会话不挂载任何未显式授权的 ACP 工具，仅当用户主动显式开启时才暴露给大模型。
- **ACP 子工具独立可控与智能级联（前端交互重构）**：
  - 解除子工具开关禁用状态：大类无论开启或关闭，展开后子工具开关均可直接点击；
  - 智能级联激活：在大类关闭状态下，点击某个子工具开启时，系统自动将该大类设为开启，并且仅开启当前点击的这个子工具，其余子工具保持关闭；
  - 智能级联关闭：关闭某个大类下最后一个开启的子工具时，大类总开关自动切为关闭状态；
  - 批量快捷控制：在大类展开区提供“全部启用”与“全部禁用”快捷按钮，支持一键批量配置。
- **MCP 协同对齐（仅优化子工具独立级联与批量控制，保持既有默认策略不变）**：
  - 严格保持 MCP 既有默认配置策略、鉴权与连接逻辑完全不变，不改变其默认启用/禁用规则；
  - 解除未连接/禁用状态下的子工具操作死锁：展开后允许直接操作子工具；
  - 点击未激活 MCP Server 下的子工具时，自动级联激活该 MCP Server，且仅开启当前被点击的工具；
  - 在 MCP Server 展开区提供“全部启用”与“全部禁用”快捷按钮，与 ACP 交互范式彻底对齐。
- **VS Code 与 IntelliJ IDEA 宿主配置隔离**：
  - 前端感知当前宿主平台类型（`vscode` 或 `intellij`，通过能力类别或环境标识自动确定）；
  - `opencode.json` 中的 `acp` 配置结构按宿主平台实施命名空间分层：`acp[platform][categoryId]`；
  - 向后兼容：优先读取平台命名空间配置，若不存在则回退兼容历史扁平配置 `acp[categoryId]`；
  - 核心运行时（`packages/opencode/src/session/tools.ts`）在动态装配工具时，优先匹配当前 Bridge 宿主平台的配置块。
- **自动化测试**：
  - 前端单测覆盖 ACP 与 MCP 默认禁用、级联开启/关闭、一键全选/全不选以及平台命名空间读写；
  - 核心层单测覆盖多平台命名空间配置解析与工具过滤。

# 非目标

- 本期不修改 MCP 既有的默认启用/禁用策略、底层注册逻辑与模型工具注入策略，仅优化面板开关交互。
- 本期不更改已有 LSP、Plugins 等其它功能模块的配置格式。
- 本期不修改 IDE 宿主端 Bridge 的底层通讯格式（RPC 协议保持不变）。

# 验收示例

- Scenario: A1 默认全量禁用（仅限 ACP）
  - GIVEN 一个未配置过 ACP 的项目
  - WHEN 用户打开 ACP 状态面板，或 AI 会话初始化
  - THEN 所有 ACP 大类与子工具均显示为未启用（0/N 启用），大模型工具列表不包含任何未授权 ACP 工具（MCP 既有默认策略保持不变）

- Scenario: A2 ACP 与 MCP 关闭状态下独立开启子工具并智能级联激活
  - GIVEN 某个 ACP 大类或某个 MCP Server 当前处于关闭/未启用状态（0/N 启用）
  - WHEN 用户展开该卡片并点击其中一个子工具的开关开启
  - THEN 该子工具变为开启，父级总开关（ACP 大类或 MCP Server）自动级联激活为开启，且其它子工具依然保持原有状态，不被全量勾选（1/N 启用）

- Scenario: A3 ACP 与 MCP 关闭最后一个子工具自动闭合父级
  - GIVEN 某个 ACP 大类或某个 MCP Server 仅开启了 1 个子工具（1/N 启用）
  - WHEN 用户点击关闭该子工具
  - THEN 该子工具变为关闭，父级总开关自动联动切换为关闭（0/N 启用）

- Scenario: A4 ACP 与 MCP 一键全部启用与全部禁用
  - GIVEN 某个 ACP 大类或某个 MCP Server 展开展示了多个子工具
  - WHEN 用户点击“全部启用”或“全部禁用”快捷按钮
  - THEN 该分类下的所有子工具批量同步为全开（N/N 启用）或全关（0/N 启用）

- Scenario: A5 VS Code 与 IntelliJ IDEA 双端配置命名空间隔离与平滑回退
  - GIVEN 同一个项目分别在 VS Code 和 IntelliJ IDEA 中打开并配置了各自的 ACP 开关
  - WHEN 保存配置到 opencode.json
  - THEN 双方的配置分别存储在 acp.platform_vscode 与 acp.platform_intellij 下，互不覆盖，且对历史无平台命名前缀的扁平配置提供平滑读取兼容

# 约束与不变量

- 保持配置持久化与界面状态的高效乐观更新（Optimistic Update）和并发锁保护。
- 保证配置结构对旧版 `opencode.json` 的完全向下兼容。
- 遵循 Strict Allowlist 原则：只有明确配置为 true 的工具才注册给大模型。
- 遵循 MCP 协议的动态生命周期特性：MCP 工具目录在初次握手连接后建立，由项目作用域存储持久化支持离线目录保留与 0/N -> 1/N 级联开启；无历史元数据的全新禁用 Server 经由初次启动连接后自动捕获并持久化目录。

# 决策

- 已确认：ACP 默认值从 `true` 改为 `false`，实现开箱即用的安全与最小权限；MCP 既有默认策略保持不变。
- 已确认：大类 / MCP Server 关闭时子工具解禁，点击子工具采用级联单开，彻底消除大类下一开全开的体验问题。
- 已确认：ACP 与 MCP 在状态面板中的展开、子工具独立开关、快捷全选全关采用统一设计规范。
- 已确认：在 `opencode.json` 的 `acp` 字段下采用平台命名空间隔离（`platform_vscode` 与 `platform_intellij`），杜绝双端重名大类（如 `tasks_and_problems`）的配置互相覆盖。

# WebGUI 执行中补充与排队输入

## 目标与范围

当前 WebGUI 的 Composer 提供执行中继续输入、选择发送方式、待发送列表管理与停止后恢复能力。服务端持久化待发送输入，统一决定何时加入正式对话和模型上下文。能力覆盖 IDE 共用 WebGUI 与普通浏览器，不迁移其他客户端到新的 Session 实现。

## 提交交互

空闲会话中，非空输入按既有方式发送。执行中，Enter 打开发送方式弹窗，提供“立即补充”“排队发送”和取消；两个选项分别说明“当前响应与工具完成后，在下一次模型调用时加入”和“当前任务完成后再发送”。停止按钮继续承担停止用途，不替换为发送动作。Shift+Enter 换行，IME 组合输入的 Enter 不提交。

打开弹窗时绑定当前会话与输入快照。用户取消、Escape 关闭或切换会话时，不提交、不丢草稿、不向切换后的会话误发。选定方式后先请求准入，等待时防止重复确认；准入成功后只清除对应已提交草稿，保留期间新写入的内容并让编辑器可以继续输入。失败提示原因并保留内容，不能因准入失败把正在执行的会话标为空闲。

弹窗打开时会话可能已完成：服务端以准入时实际状态处理，未暂停且已空闲时可以立即执行，不要求客户端盲目重试。优雅停止中的提交允许进入暂停列表，但不能绕过停止启动模型。

快捷短语保留现有双击发送和回填行为；本次不扩展其忙碌时的发送入口。输入框中已识别的服务端 slash command 必须保留命令语义与参数，可作为待发送项；只在选中的消费边界展开为正式输入，不在准入时提前执行。客户端本地管理动作不转成发给 LLM 的普通文本。

## 待发送栏

统一 Composer 内，待发送栏置于快捷短语下方、附件和编辑区上方，与现有面板共用圆角与主题。仅有消息时显示。列表按服务端提交顺序展示，切换会话默认收起。

收起时展示首条消息、模式、单行内容摘要、总数和展开按钮；展开后逐条展示，长列表在有界高度内滚动，避免遮挡编辑器。附件型输入显示可读文件摘要。展开状态不代表执行优先级。

每条补充仅显示“转排队”和删除按钮；每条排队仅显示“转补充”和删除按钮。当前模式按钮隐藏。转换不改 ID、快照和提交序号。删除按钮提供“删除待发送消息”的可访问名称。操作进行中禁用该项重复操作，失败显示原因并保留服务端有效状态。

暂停时顶部显示“已暂停”；停止完成且会话空闲时提供“发送下一条”。运行或停止未完成时该按钮不可触发重复执行。消费成功的项移出待发送栏并进入正式对话，不留第二份乐观 user 消息。删除最后一条后移除整个栏。

## 执行规则

### 立即补充

不取消当前流式响应，不打断工具。当前响应及其关联工具完成后，在构造下一次正常 provider 请求历史前取得已准入 steer 的有序批次。按顺序写入独立 user 消息，重新加载包含这些消息的上下文，再发起一次模型请求。

例如 A、B、C 在同一边界前成功准入，下一次请求包含 A → B → C，C 为最新 user。不会只保留 C，也不会为了三条输入启动三个并发请求。该批之后准入的 D 留给后续边界。每个输入保留自己的提交配置；这一轮由最新 user 的 Agent、模型和 variant 决定，同既有最新用户输入语义。新增用户输入重置其对应的后续 provider-turn 额度；一批补充只重置一次。

自然完成响应与新补充交错时，未暂停且已准入的补充仍得到后续执行。终止性错误、手动停止或重启恢复优先于自动消费。

### 排队发送

queue 不进入当前任务的工具后续请求。只有当前任务不再需要后续 LLM 或关联工具处理、准备自然空闲时，才提取最早的一条 queue 并开始新任务。完成该条任务后再考虑下一条。即便 provider 返回 stop，如果仍有需要模型处理的工具结果，也不算自然完成。

每个执行边界先处理 steer；它们可以越过列表中更早提交的 queue。按序批量补充后必须重新判断任务是否完成，不能同时带入排队项。准入、暂停变更、批次截止序号与 queue 首项选择在同一会话锁/事务内串行裁决：截止前的 steer 优先，截止后的输入等待后续边界，不追溯改变已确定的请求。准入、自然退出与重新唤醒使用统一 Session 协调，避免退出窗口留下永远不执行的已接收消息。

## 停止与恢复

第一次手动停止首先暂停本会话待发送消费，再沿用优雅停止：当前响应和工具安全收尾，不启动后续模型调用。再次点击仍使用现有强制停止确认；取消确认继续等待，确认则立即取消。现有问题/权限拒绝、等待横幅及空闲后焦点恢复保持。

暂停与消费领取共用服务端裁决点；暂停先成功就禁止后续领取和新请求启动，领取先完成则该项已进入正式历史、不可撤回，但请求尚未启动时仍须遵守停止检查。尚未消费的补充和排队全部保留。已被消费进入当前请求的消息不再提供删除/转换，不承诺撤回。停止中的新提交也保留在暂停列表。

停止完成后点击“发送下一条”：按展示顺序显式取第一条，不受该条模式影响；以这一条启动第一轮请求，同时解除暂停。余下 steer 等下一次安全边界，queue 等任务自然完成。并发点击或多窗口恢复只能启动一个执行者。

暂停且已空闲时，用户手动发送新草稿只启动新草稿，旧列表继续暂停；转换模式、删除、刷新、切换会话均不恢复消费。只有显式“发送下一条”恢复旧列表。该规则避免用户先发一句说明就意外触发全部积压任务。

provider 可重试错误继续服从现有 retry 策略；不因此消费 queue。终止性错误保留未消费项并暂停。后端重启保留队列，恢复时暂停，等待显式“发送下一条”；不得因为恢复队列自动重试崩溃前已开始的 provider 请求。已经正式消费的输入仍保留在对话历史。如果历史已写入但请求尚未开始就停止或崩溃，该输入保留为尚未获得回答的正式消息，用户通过现有会话重试/继续能力显式继续，不重复入队或复制 user 消息；提供可理解的未完成状态与恢复入口。若无法判断 provider 是否已经开始，同样只允许显式继续，不承诺 provider 调用恰好一次。

## 并发与可靠性

准入成功表示服务端已持久化，未表示模型已收到。每条输入具有稳定 ID、Session ID、单调提交顺序、delivery、完整提交快照及生命周期信息。重复准入同 ID 且完整原始提交快照一致返回既有结果；快照包含文本/parts、附件、命令参数、Agent、模型、variant 与原始 delivery，任何冲突或跨会话复用都失败。模式修改不改变原始重试身份。

消费、转换、删除以服务端一致性边界裁决。转换或删除先成功则消费遵守新状态；消费先成功则拒绝后到操作并返回已发送状态，让 UI 对账。不得先从队列删除再冒险写历史。正式历史与消费标记采用可原子完成或可幂等恢复的持久化过程，保证进程故障不丢未消费消息、不重复创建 user 消息。

同一后端进程内的多个窗口、跨目录 WebGUI 和刷新恢复使用服务端快照与变更事件。快照与事件带可比较版本，迟到快照/事件不覆盖新状态，不复活删除项或已消费项。网络失败不伪造成功；用稳定 ID 安全重试。切换会话后的响应不得污染当前会话。

信任边界校验非空输入、合法 delivery、已有会话、目标输入所属会话与可修改生命周期。会话删除清理其队列；持久化存储与既有权限和目录路由一致。附件使用已有数据结构，准入时保存用户提交的数据；文件引用仍遵守现有读取语义，不新增全文件快照体系。

## 实现方案与验证

### 已调查事实

- `packages/opencode/webgui/src/components/MessageInput/index.tsx` 中 `sendLocked = busy || interactionLocked` 阻止运行中回车；编辑器可编辑性只受 interactionLocked 控制。
- `hooks/useMessageInput.ts` 通过 `sdk.session.prompt` 提交并在现有提交过程中清空编辑器，提交请求可持续到执行结束，不能直接用其请求锁阻塞连续准入。
- legacy `SessionPrompt.prompt` 当前先创建正式 user 消息再调用 loop；`runLoop` 在循环首部读取历史，具有自然结束与 gracefulStops 检查。
- `SessionRunState.ensureRunning` 负责单会话运行协调；保留其串行执行职责。
- Core V2 已存在 steer/queue 语义，但当前 WebGUI 的 HTTP handler 调用 legacy SessionPrompt；直接调用 V2 输入表不能驱动该执行链路。

### 选定方案

在当前 legacy Session 域增加持久化待发送输入边界，复用仓库数据库、Schema、事件桥和单会话锁/runner 模式。HttpApi 提供准入、快照、转换、删除和发送下一条操作；Composer 通过生成 SDK 使用这些能力。正常空闲发送兼容现有协议，停止入口统一暂停待发送列表。

在实际 runner 的安全边界调用消费逻辑；对自然完成、终止性错误和停止分别处理，不从浏览器订阅 idle 后代发。持久化/消费细节收口在队列模块，前端只处理草稿、选择和显示，不另建一套执行状态机。Schema/Core/Protocol/Server/Client 保持项目规定的运行时依赖方向。

不选择纯前端队列：页面关闭后无法派发、无法可靠确认 provider 边界，多窗口也会重复发送。不选择整体 V2 迁移：超出当前功能所需改动。具体存储字段和锁实现由 Build 在现有基础设施内确定，必须满足上述幂等和暂停规则。

### 交付检查

验收项统一使用 brief.md 的 A1–A12，避免重复生成同义场景。后端测试实际 provider 请求中的 user 顺序、批量与逐条边界、暂停恢复和竞争；前端测试真实组件交互及异步状态恢复。SDK 从源定义生成，不直接编辑生成目录；类型检查从受影响 package 运行。按用户在 Build 阶段明确提出的要求，后续由当前 Agent 自行实现、测试与检查，不调用子代理；未执行或受环境阻塞的检查必须明确报告。

UI 延用现有主题和 Composer 结构，弹窗复用现有可访问模态能力，操作提供键盘焦点、可访问名称和请求反馈；浅色、深色、窄屏及长内容均不能遮挡发送/停止操作。不增加运行时依赖。

# Outcome

在当前 IDE 插件共用的 WebGUI 中，允许用户在 AI 执行期间连续提交补充或排队提示词，并在消息进入上下文前管理发送方式和删除消息。补充不打断当前调用，排队等待当前任务自然结束；手动停止后保留待发送消息并提供明确的恢复入口。

# Scope

- WebGUI Composer 的回车提交、方式选择弹窗、输入框上方待发送栏、会话切换与事件恢复。
- 当前 WebGUI 实际调用的 legacy SessionPrompt 链路，增加服务端持久化待发送输入及安全消费边界、列表查询、模式切换、删除、发送下一条和事件同步。
- 保留现有文本、附件、文件引用、Agent、模型和 variant 的提交数据。已识别的服务端 slash command 在入队后延迟执行其命令语义；不把命令静默变成普通文本。
- 与现有优雅停止、强制停止、权限与问题处理、跨目录会话同步兼容。
- 单个 Native change。前后端验收共同依赖发送状态机和同一执行边界，拆分会重复改动核心区域，不采用 Supervisor Change。

# Non-goals

- 不迁移整个 WebGUI 到 V2 Session，不让 V2 runner 调用 legacy loop。
- 不实现 Codex turn RPC、打断后合并重提交、sleep/wait 工具加速或 TUI 队列 UI。
- 不增加消息编辑、拖拽排序、定时发送、批量删除或独立队列设置页。
- 不改变快捷短语的双击发送/回填约定、后台任务本身的生命周期、已有权限策略和 provider retry 策略。
- 不发布版本、不打包插件、不推送或创建 PR。

# Acceptance examples

- A1：空闲时回车直接发送；运行中回车打开“立即补充／排队发送”弹窗；取消保留草稿，确认成功清空并可连续提交；Shift+Enter 换行、IME 回车确认和停止按钮保持正确。
- A2：当前响应与关联工具完成后，只批量接收列表开头连续的补充消息并按顺序作为独立 user 消息进入下一次 LLM 请求；排队消息后的补充不得越过屏障，边界后到达的输入等待后续边界；当前响应自然 stop 时仍处理符合顺序的已接收补充。
- A3：排队消息不进入当前任务的工具后续上下文；当前任务自然结束后只启动列表最前的一条排队消息，其执行边界后才允许处理位于其后的补充，完成该条任务后再考虑下一条排队消息；含工具调用的 provider stop 不被误判为任务完成。
- A4：两种模式共享服务端顺序列表，默认展示首条及总数，支持展开收起；补充项显示“转排队／上移／删除”，排队项显示“转补充／上移／删除”，第一项不显示上移，当前模式按钮隐藏；空列表不占位，已消费项移入正式对话；删除成功的任意待发送项按确认结果回填输入框或丢弃。
- A5：模式切换保持 ID、内容和顺序；上移将当前待发送项与前一项原子交换并同步到多窗口，用户把补充移到排队消息前后该补充才可提前释放；删除只在服务端确认成功后回填完整文本和附件，与消费竞争失败时不修改草稿；重排、转换、删除与消费竞争时服务端只接受一个结果，已消费项不可伪装成操作成功。
- A6：第一次手动停止即暂停待发送列表，优雅收尾和确认强制终止均不自动消费剩余消息；停止过程中仍可编辑或提交到暂停列表，模式转换不启动 AI，保留既有两阶段停止和审批拒绝行为。
- A7：停止结束后“发送下一条”按展示顺序启动第一条并恢复自动消费，运行中不可重复启动；暂停时手动发送一条新草稿只执行该草稿，不暗中恢复旧列表；空列表不显示恢复操作。
- A8：终止性执行错误或后端重启后保留未消费输入并暂停，provider 可恢复重试期间不提前派发排队项；刷新、切换会话和跨目录会话恢复列表与暂停状态，多窗口修改可同步；历史已写入但请求未开始即停止/崩溃时，正式消息不重复且可由现有重试/继续入口恢复。
- A9：提交响应丢失后以同一消息 ID 和完整原始快照重试不重复入队或重复进入历史，不同附件、模型、variant 或原始 delivery 的冲突重试失败；非法模式、空输入、不存在会话及跨会话操作被拒绝；快照/事件乱序不能复活已删除或已消费项；准入、停止和消费竞争有单一会话裁决顺序。
- A10：提交时文本、图片、文件引用、Agent、模型、variant 保留；连续补充同批使用最新补充选择驱动下一次 LLM 请求；slash command 保持命令语义，失败保留可恢复提示且不消费后续输入。
- A11：弹窗支持键盘选择、Escape 取消、焦点返回；删除时若输入框为空则成功后自动回填，若非空则先选择“覆盖输入框并回填”或“保留当前草稿并丢弃待发送内容”，取消不删除；列表操作有可访问名称、状态反馈，浅色/深色及窄屏不遮挡编辑区或停止操作；请求失败不丢草稿、不误报会话空闲。
- A12：后端边界与竞争测试、WebGUI 提交与恢复交互测试、受影响包类型检查及必要 SDK 生成完成；按用户最新要求，由当前 Agent 自行检查，不启动子代理。

# Constraints and invariants

- 以服务端准入确认与正式历史消费分离为核心，不依赖浏览器存活或客户端 idle 事件派发消息。
- 单会话只有一个执行者；补充、排队和手动恢复都通过既有 SessionRunState 协调，不新开并行模型循环。
- 持久化队列按 Session ID 隔离，使用当前 Session 的目录路由；不新建私有 SQLite 文件，不直接写生成代码。
- 消费、模式修改、删除在同一一致性边界裁决。数据库保存成功才返回准入成功，正式历史写入成功才移除待发送项；崩溃恢复不得自动重放已开始的 provider 请求。
- 不撤销已经进入当前请求的输入；“立即”指下个安全请求边界。
- 类型检查使用受影响 package 中的 `bun typecheck`；测试从 package 目录运行，SDK 使用 vfox 管理的工具。

# Decisions

- D1：沿用当前 `ide-plugin` 分支与目录，创建 `webgui-input-queue`；工作区在创建前干净，无其他 active change。
- D2：两种模式分别为 steer 和 queue，UI 文案为“立即补充”和“排队发送”。
- D3：当前模式对应转换按钮隐藏，明确取代先前“禁用”建议。
- D4：多条补充按提交顺序在同一安全边界批量消费，各自保留 user 消息；新到达输入等待后续边界。
- D5：手动停止先暂停待发送消费；保留列表，空闲后“发送下一条”启动首条并恢复后续自动消费。
- D6：暂停期间新草稿可单独发送，旧列表保持暂停；只有“发送下一条”恢复旧列表。停止尚未完成时提交的输入仍进暂停列表。
- D7：待发送输入服务端持久化，刷新与窗口切换不丢失；终止性错误、进程重启时暂停未消费输入，避免自动重试模型工作。
- D8：列表顺序表示提交顺序；执行中 steer 可越过更早的 queue；手动恢复时显式取展示首条。
- D9：以当前 legacy 链路实现，复用已有存储、锁、事件和 runner；V2 Session 能力仅作为语义参考。
- D10：以上规则连同验收项进入 Comet 最终 Shape 确认；确认后按同一 change 完成实现与独立验收。
- D11：用户确认进入 Build 后明确要求“直接实现，不用子代理”，因此后续实现、测试与检查由当前 Agent 完成，取代 D10 的子代理验收安排；不伪造独立验收结果或通过手改 Runtime 状态归档。
- D12：列表顺序取代模式优先级成为权威执行顺序；排队消息是屏障，后续补充不能自动越过。非首项可上移一位，服务端原子交换相邻顺序；用户主动移到屏障前视为明确改变释放顺序。
- D13：删除适用于两种 delivery。输入框为空时，服务端确认删除后自动回填该项完整文本与附件；输入框非空时先让用户选择覆盖回填或保留当前草稿并丢弃该项，取消不发删除请求。消费竞争导致删除失败时不改输入框。

# 图片生成结果项目内落盘与路径引用设计

## 背景

当前图片生成链路已经支持：

- `image_generation` 最终结果识别。
- 将图片挂到 `ToolStateCompleted.attachments`。
- WebGUI 展示缩略图与预览。
- 后续对话通过附件把图片再次回放给模型。

但现状仍以 `data:image/...` 作为图片主载体，带来几个问题：

- 会话历史体积大。
- 历史记录保存的是图片内容，而不是项目内可复用资产。
- AI 后续使用图片依赖系统自动喂图，而不是像处理普通项目文件一样主动查看。

本次设计目标是把生成图片改成“首次生成即写入当前项目临时目录，历史只保存文件引用路径，前端按路径加载展示，后续 AI 只收到路径并自行查看文件”。

## 目标

实现以下行为：

- 图片首次生成后，自动保存到当前项目的 `.opencode/generated-images/`。
- 会话历史只保存项目相对路径引用，不再长期保存 base64 图片内容。
- WebGUI 仍显示缩略图与预览，但数据来源改为项目文件路径。
- 历史会话重新打开时，只要文件仍存在，仍可显示图片。
- 后续 AI 回放时只看到路径，不再自动收到图片内容。
- 生成的图片默认长期保留，除非用户手动删除。

## 非目标

本次不包含：

- 自动清理历史生成图片。
- 会话删除时联动删除图片文件。
- 通用任意文件静态服务。
- 对旧历史消息做批量迁移。
- 新的图片资源管理面板。
- `partial_image` / `partial_images` 的中间预览策略改造。

## 存储位置与生命周期

### 目录位置

所有新生成图片统一写入当前项目：

```text
<project>/.opencode/generated-images/
```

该目录语义明确：

- 属于 opencode 自己管理的项目内临时资产。
- 与项目绑定，方便 AI 和用户通过相对路径引用。
- 适合默认加入忽略规则或由用户自行忽略。

### 生命周期

- 图片一旦成功写入，默认长期保留。
- 系统不自动清理，不按会话生命周期删除。
- 若用户手动删除文件，会话历史仍保留其引用路径。

## 数据模型

### 总体原则

新写入格式的核心真相不再是内嵌图片内容，而是“本次工具生成了哪些项目内图片文件”。

### 附件结构

继续沿用 `ToolStateCompleted.attachments` 作为 UI 展示入口，但附件语义从“内嵌媒体”改为“项目文件引用”。

建议对图片附件保存以下最小信息：

```ts
{
  type: "file",
  mime: "image/png",
  filename: "generated-image-<messageID>-1.png",
  relativePath: ".opencode/generated-images/generated-image-<messageID>-1.png",
  source: {
    type: "tool",
    tool: "image_generation"
  }
}
```

其中：

- `relativePath` 保存项目相对路径，不再是 `data:image/...`。
- `filename` 用于 UI 文案和保存行为。
- `mime` 用于渲染和访问路由校验。

`url` 继续保留为运行时可访问地址，由前端根据 `relativePath` 生成。这样可以避免把“项目文件路径”和“浏览器访问地址”混在同一字段里。

### 输出文本

`output` 仍只保留汇总摘要：

```text
已生成 1 张图片：
```

不在 `output` 中重复拼接路径或文件名，避免工具文本噪音。路径属于附件元数据和回放数据的一部分，不属于摘要文案。

## 文件命名策略

新文件名应稳定、可读、且尽量避免碰撞。

推荐优先级：

1. `generated-image-<messageID>-1.png` 这种命名作为默认规则，保证跨消息唯一。
2. 同一条工具结果中的多张图继续按 `-1`、`-2` 顺延。

设计要求：

- 同一条工具结果中的图片顺序必须稳定。
- 文件名必须可直接映射 UI 中的 `Image #N`。
- 若目标文件名已存在，必须安全顺延或加唯一后缀，不能覆盖旧图。

## 后端数据流

新链路如下：

```text
provider image_generation result
  -> 解析最终图片 base64 / data URL / structured result
  -> 解码二进制并识别 mime
  -> 确保 <project>/.opencode/generated-images/ 存在
  -> 生成唯一文件名
  -> 写入图片文件
  -> 构造“文件引用附件”
  -> completed state 中保存摘要 + 路径附件
```

### 成功条件

只有在图片已成功写入项目目录后，才认为该图片附件可进入 completed state。

### 落盘失败策略

不回退到旧的 base64 长期存储模式。

原因：

- 一旦回退，会让新旧模型同时存在于新消息里，行为不可预测。
- 用户已经明确要求改成“文件落盘 + 路径引用”。

因此落盘失败时，应显式进入错误分支，而不是悄悄回退为 data URL。

## WebGUI 访问与展示

### 展示目标

对话界面仍保留：

- 缩略图
- 点击预览
- 路径展示

推荐 UI：

- 每张图仍显示 `Image #N`
- 文件名
- 项目相对路径，如 `.opencode/generated-images/generated-image-<messageID>-1.png`

### 图片访问方式

前端不能直接用项目相对路径作为 `<img src>`，因此需要后端提供受限访问路由，把相对路径转换为浏览器可访问资源。

示意：

```text
/app/generated-image?path=.opencode/generated-images/generated-image-<messageID>-1.png
```

前端只负责：

- 读取附件里的相对路径。
- 调用 helper 生成访问 URL。
- 用该 URL 渲染缩略图与预览。

### 历史会话显示

历史会话重新渲染时：

- 若路径对应文件仍存在，则继续显示图片。
- 若文件已不存在，则显示路径文本和“预览不可用”降级状态。

历史记录不因文件缺失而失效；它记录的是“引用了哪个项目文件”。

## 访问路由安全边界

生成图片访问路由必须是专用受限通道，而不是任意文件读取接口。

必须限制：

- 只允许当前项目目录下的路径。
- 只允许 `.opencode/generated-images/` 前缀。
- 只允许图片文件类型。
- 拒绝 `../` 等路径逃逸。
- 读取不到文件时返回明确错误状态。

这样既能满足 WebGUI 展示，又不会放开整个工作区文件访问面。

## 上下文回放策略

这是本次设计的核心行为变更。

### 新策略

后续 prompt 回放时：

- 不再把该图片自动作为模型可直接查看的 media 内容再次喂入。
- 只把生成结果的路径信息回放给模型，且由 `toModelMessagesEffect` 统一把路径转换成简洁文本上下文。

模型应在上下文中看到类似事实：

- 之前生成了 1 张图片。
- 文件位于 `.opencode/generated-images/generated-image-<messageID>-1.png`。

如果 AI 需要继续理解图片内容，应自行读取或查看该文件。

### 原因

- 这是用户明确要求的交互模型。
- 让图片更像项目资产，而不是隐藏在历史里的多模态内嵌媒体。
- 避免长会话重复注入大量图片内容。

### 影响

- 多模态模型不会自动继承“已经看过图”的能力。
- 但 AI 可通过文件路径重新查看，行为更显式、更可控。

### 路径上下文格式

建议以简洁文本形式回放，例如：

```text
已生成图片文件：.opencode/generated-images/generated-image-<messageID>-1.png
```

这样既保留可读性，也不污染工具摘要。

## 兼容策略

### 旧历史消息

旧消息里如果仍是 `data:image/...` 形式：

- 前端继续兼容显示。
- 不强制迁移旧历史。

### 新写入消息

新生成图片只写入新格式：

- 项目相对路径引用。
- 少量元数据。

### 读写分离原则

- 读取层兼容“旧 data URL 格式 + 新路径引用格式”。
- 写入层只写新路径引用格式。

这样可以避免一次性历史迁移，同时确保系统逐步收敛到新模型。

## 错误处理

### 图片生成成功但落盘失败

- 该图片不进入最终路径附件列表。
- tool result 应进入明确错误或降级提示。
- UI 提示“图片已生成，但保存到项目目录失败”。

### 历史文件缺失

- 保留路径文本。
- 图片区域显示“预览不可用”或“文件不存在”。
- 不影响其他消息渲染。

### 非法路径访问

- 访问路由直接拒绝。
- 不暴露项目外真实路径。

### 非图片输出或异常结果

- 保留原始工具文本或摘要。
- 不生成错误的文件引用附件。
- 不因单个异常结果导致会话崩溃。

## 测试策略

### 后端单元测试

- base64 / data URL / structured result 能成功落盘。
- completed state 中保存的是相对路径引用，而不是 data URL。
- 已有文件存在时，文件名会安全去重或顺延。
- 非图片结果不会生成错误文件。

### 后端集成测试

- `image_generation` 完成后，tool state 包含摘要与路径附件。
- 下一轮 prompt 回放时，只包含路径信息，不包含图片 media 回放。
- 历史引用在文件存在时可再次解析为预览资源。

### 前端组件测试

- 图片卡片显示缩略图、文件名、相对路径。
- 点击卡片可打开预览。
- 文件缺失时显示降级状态。
- 旧 data URL 格式仍可显示。

### 路由测试

- 允许读取 `.opencode/generated-images/*`。
- 拒绝 `../` 路径逃逸。
- 拒绝非图片文件。
- 文件不存在时返回正确错误。

## 实现影响面

预计主要影响：

- `packages/opencode/src/session/generated-image.ts`
  - 从“生成 data URL attachment”改为“落盘并生成路径引用 attachment”。
- `packages/opencode/src/session/processor.ts`
  - 保持图片结果归一化接入点，但新增文件写入失败处理。
- `packages/opencode/src/session/prompt.ts`
  - 调整后续回放逻辑，确保只回放路径信息。
- WebGUI 图片附件展示组件
  - 从直接使用 `attachment.url` 改为通过路径生成可访问图片 URL。
- WebGUI 图片预览组件
  - 兼容路径型资源与旧 data URL 资源。
- 后端图片访问路由
  - 新增专用安全访问入口。

## 设计结论

本次设计将图片生成结果从“会话内嵌媒体”调整为“项目内文件引用”：

- 首次生成即写入 `./.opencode/generated-images/`
- 会话历史只保存项目相对路径和必要元数据
- WebGUI 通过受限路由按路径加载缩略图与预览
- 后续 AI 只收到路径，不自动收到图片内容
- 旧历史记录继续兼容显示，但新写入不再使用 data URL

这与用户期望完全一致，也让生成图片更接近普通项目资产文件的使用方式。

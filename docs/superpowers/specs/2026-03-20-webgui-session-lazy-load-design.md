# WebGUI 会话惰性加载

## 背景

当前 `packages/opencode/webgui` 存在两处全量加载。`SessionContext` 通过 `sdk.session.list()` 全量拉取会话，`MessagesContext` 通过 `sdk.session.messages({ path: { id } })` 全量拉取消息。

这会让 WebGUI 在大会话和多会话场景下明显变慢，首屏等待、切换会话和长会话滚动体验都受影响。

仓库内已有可参考能力。`packages/app` 已支持会话列表的 `limit/trim`、消息的 `before + limit` 分页，以及 `prefetch / cache / eviction` 一类按需加载机制。

服务端现有 API 已满足第一阶段需要。`session.list(limit)` 可限制列表返回量，`session.messages(limit, before)` 可按页返回消息，并通过 `X-Next-Cursor` 提供下一页游标。

---

## 目标与非目标

### 目标

- 同时优化会话列表和消息加载
- 会话列表只加载首屏，并支持继续加载更多
- 打开会话时先显示最近一页，再按需补历史
- 在不新增服务端协议的前提下显著降低首屏和长会话成本
- 保持底部实时区稳定，兼容 SSE 新消息、`question`、`permission` 和回到底部体验

### 非目标

- 第一版不做冷页淘汰
- 第一版不为 `session.list` 新增 cursor 协议
- 第一版不做复杂预取
- 第一版不追求滚到极顶部时仍维持最小 DOM

---

## 比较方案

### 最小改动分页

只给列表和消息加基础分页，界面层尽量少改。优点是实现快、风险低，缺点是很难同时解决底部实时区稳定性和长会话 DOM 成本。

### 轻量分层加载

列表与消息分别按需加载，并让消息列表只做顶部单向卸载。优点是能直接复用现有 API，同时兼顾首屏、历史翻页和底部实时区稳定性。

### 伪全量后台补齐

首屏先拉一部分，再在后台继续补齐到“接近全量”。优点是上层调用心智接近现状，缺点是后台补齐仍会回到高请求量和高 DOM 成本。

### 结论

推荐轻量分层加载。它在不改服务端协议的前提下，覆盖了当前最主要的性能瓶颈和交互约束。

---

## 推荐方案

整体方案分两层。会话列表按“首屏 + 更多”工作，消息按“最近页优先 + 向上补历史”工作。

渲染层不采用传统双向 virtualization，而采用“顶部单向卸载、底部始终保留”的 DOM 策略。它只从会话顶部往下逐渐卸载 DOM，绝不卸载当前视口到会话底部的所有消息 DOM。

已卸载部分只移除 DOM，不删除已加载数据。顶部通过占位高度维持滚动条长度和滚动位置稳定。

这个策略主要服务于底部实时区。SSE 新消息、`question`、`permission`、流式输出和“回到底部”都依赖底部区域持续稳定存在。

需要明确接受一个 trade-off。用户一旦滚到很靠近顶部，几乎整段会话会重新挂回 DOM，此时优化效果会明显下降，但这是为了换取底部实时区稳定性而有意接受的取舍。

---

## 架构设计

本次改动只使用现有服务端能力，不新增协议。客户端拆分为列表层、消息层和渲染层三个关注点。

列表层只管理会话元信息。消息层按 `session` 维度管理消息页、游标和加载状态，渲染层负责顶部单向卸载、占位高度和滚动补偿。

会话激活逻辑从“切换后默认全历史已到齐”改为“切换后只保证最近页可用”。这样可以让加载语义与真实分页状态保持一致。

---

## 组件边界

### SessionContext

`SessionContext` 只负责会话元信息列表，不负责消息内容。它新增 `limit`、`loading`、`loaded`、`hasMore`、`loadMoreSessions` 等状态与接口。

初始化时只拉首屏。用户请求更多时，增大 `limit` 并重新调用 `session.list(limit)`。

### MessagesContext

`MessagesContext` 按会话管理消息页和元数据。核心状态包括 `messagesBySession` 与 `pageMeta`，其中 `pageMeta` 至少包含 `cursor`、`complete`、`loading`、`loaded`、`error`。

它提供 `loadLatest`、`loadOlder`、`ensureSession`。切换会话时只拉最近一页，向上滚动时再用 `before + limit` 获取更旧页。

同一会话已加载的数据可缓存复用。第一版保留缓存，不引入冷页淘汰。

### MessageList

`MessageList` 负责顶部单向卸载。它处理顶部 sentinel、历史 prepend 后的滚动补偿，以及顶部占位高度。

它不会裁掉当前视口到底部的消息 DOM。底部保留区始终存在，用来承接实时追加和底部交互。

### App / useSessionActivation

`App` 与 `useSessionActivation` 只触发 `ensureSession`。它们不再假设切换会话后全历史会立刻到齐。

加载中和错误态 overlay 只表示“最近页首屏是否可用”。旧历史页失败不应阻断当前会话已显示的最新内容。

---

## 数据流

### 会话列表

应用初始化时，`SessionContext` 以首屏 `limit` 调用 `session.list(limit)`。返回结果直接替换列表视图，并结合返回量判断 `hasMore`。

用户点击“更多”后，客户端只增大 `limit` 并重新请求。第一版不做列表级 cursor 分页。

### 会话激活

用户切换到某个会话时，`useSessionActivation` 调用 `ensureSession(sessionID)`。若该会话最近页已在缓存中，则直接复用，否则调用 `loadLatest(sessionID)`。

`loadLatest` 使用 `session.messages(limit)` 获取最近一页，并记录 `X-Next-Cursor` 对应的下一段历史游标。最近页成功后，页面即可进入可用状态。

### 历史翻页

用户向上滚动接近顶部 sentinel 时，`MessageList` 触发 `loadOlder(sessionID)`。`MessagesContext` 用当前 `cursor` 调用 `session.messages(limit, before)` 拉取更旧消息。

旧页返回后，消息会 prepend 到已加载数据前面。`MessageList` 在 DOM 更新后做滚动补偿，保证用户视口锚点稳定。

### 实时追加

SSE 新消息到达时，消息直接追加到底部保留区。若用户当前贴底，则自动跟随最新消息。

若用户不在底部，则不强制跳转。界面可以提示“有新消息”或“跳到底部”，但底部保留区始终存在，不会因渲染裁剪而丢失 `question`、`permission` 或流式输出。

---

## 异常处理

会话列表加载失败时，应保留已加载内容，并允许用户重试。列表错误不应清空已有首屏结果。

最近页首屏加载失败时，应显示明确错误态和重试入口。因为最近页决定会话是否可进入可用状态，所以该错误属于主错误面。

旧历史页加载失败时，只影响继续向上翻历史。当前已显示内容、底部实时区和最近页可用性都应保持不变。

同一会话的 `loadOlder` 需要去重，避免重复并发请求同一页。所有异步响应都必须校验新旧关系，过期响应不能覆盖当前状态。

---

## 兼容性

本方案只复用现有服务端 API。`session.list(limit)`、`session.messages(limit, before)` 和 `X-Next-Cursor` 已能满足本次改造边界。

交互层面保持现有核心能力可用。草稿保护、选择态恢复、`revert / retry`、`subtask` 跳转和 SSE 新消息追加都必须继续工作。

方案不引入传统双向 virtualization，因此不会改变底部实时区的基本交互语义。代价是滚到极顶部附近时，DOM 优化会有意退化。

---

## 测试与验收

### 功能验收

- 会话列表首屏不再全量加载，只请求首屏数量
- 只有在用户请求更多时，列表才通过扩大 `limit` 继续加载
- 打开大会话时只拉最近一页，不全量拉历史
- 向上滚动时使用 `before + limit` 分页拉取旧页
- 历史 prepend 后滚动锚点保持稳定
- SSE 新消息可直接追加到底部保留区
- 用户贴底时自动跟随，不贴底时不强制跳转

### 性能验收

- 长会话场景下，DOM 节点数相对当前实现显著下降
- 首屏加载时间和切换大会话等待时间明显改善
- 需要在验收结论中明确说明：用户滚到极顶部时，该策略会退化，DOM 优化效果会明显下降

### 回归验收

- `draft guard`
- `selection restore`
- `revert / retry`
- `subtask` 跳转
- SSE 新消息追加与底部跟随

---

## 风险与后续演进

第一类风险是顶部单向卸载的阈值和占位高度计算不当，导致滚动抖动或锚点偏移。缓解方式是把卸载、占位和 prepend 补偿都收敛在 `MessageList` 内部，并针对长会话做专项验证。

第二类风险是分页并发与过期响应处理不严，导致会话切换后状态串写。缓解方式是对同会话 `loadOlder` 去重，并在每次响应落地前校验 session 与请求代次。

后续演进可以继续沿着现有方向推进，包括冷页淘汰、更轻量的预取，以及更细的列表分页协议，但这些都不属于第一版范围。

第一版也不会追求“滚到极顶部时仍保持最小 DOM”。这一点是当前设计明确接受的边界，而不是遗漏项。

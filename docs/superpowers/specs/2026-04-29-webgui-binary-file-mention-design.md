# WebGUI 二进制文件 @引用降级设计

> 日期：2026-04-29
> 状态：待审阅

## 问题

当前 WebGUI 在输入框中通过 `@` 引用文件路径时，后端会把这类 `file://` 引用进一步解析为文件内容上下文。

这对文本文件是正确的：

- `@foo.ts` 会触发 Read，向模型提供文本内容
- `@foo.ts:3-12` 会按范围读取对应行号内容

但当目标是 `.vsix`、`.zip`、`.exe` 这类不支持展开的二进制文件时，现有链路仍会尝试走文本读取逻辑，最终由 Read 工具抛出：

- `Cannot read binary file: <path>`

实际结果是：

- 消息本身通常仍能继续执行并返回
- 但界面会出现会话错误提示，制造了错误噪音
- 用户真正想表达的往往只是“请关注这个文件路径”，而不是“请把这个二进制文件内容展开给模型”

同时，本次修复不能破坏两类已正常工作的行为：

- 文本文件的 `@路径` 与 `@路径:开始-结束` 行号范围能力
- PDF 继续作为 attachment 交给模型，而不是退化成纯路径引用

## 范围

本次只处理 **WebGUI 发送的 `@文件路径` 在后端的解析策略**。

包含：

- 调整 `packages/opencode/src/session/prompt.ts` 中 `file://` 文件引用的分流逻辑
- 让“其他二进制文件”不再触发 Read 与 Session.Error
- 保留文本文件的读取与行号范围能力
- 保留 PDF / 图片的 attachment 行为
- 补充后端回归测试

不包含：

- 修改 WebGUI 输入框的 mention 外观、插入方式或交互
- 修改 IDE host 向 WebGUI 注入路径的协议
- 新增新的前端提示文案、toast 或图标状态
- 让不支持的二进制文件自动转换成可上传附件
- 改动 TUI、CLI 或其他非 WebGUI 的文件引用交互

## 方案

采用“**后端按文件类型分流 `@文件` 引用语义**”的方案。

核心规则：

1. **文本文件**：继续按现有方式读取，可应用行号范围
2. **PDF / 图片**：继续按现有方式作为 attachment 交给模型
3. **其他二进制文件**：停止自动读取内容，只保留路径引用语义，不再报错

### 为什么选择这个方案

- 根因在后端 prompt 解析阶段；在这里修复能覆盖所有 WebGUI `@文件` 来源，而不是只覆盖某一种前端入口
- 前端 mention 协议本身已经能正确表达路径与行号范围，不需要扩大改动面
- 文本文件、PDF、图片与其他二进制文件本来就有不同语义，把它们拆开处理更符合用户预期
- 只对“其他不支持展开的二进制”降级，能避免误伤文本文件与 PDF 的现有能力

## 设计细节

### 类型分流规则

当用户消息中的 `part.type === "file"` 且 `part.url` 为 `file://` 时，后端按以下顺序判断：

1. **目录**
   - 保持现有行为
   - 仍走目录读取逻辑

2. **PDF / 图片**
   - 保持现有行为
   - 继续生成 attachment / media part
   - 不退化成纯路径引用

3. **文本文件**
   - 保持现有行为
   - 继续触发 Read
   - 若 URL 中存在 `?start=&end=` 范围参数，继续按行号范围读取

4. **其他二进制文件**
   - 不调用 Read
   - 不尝试把文件内容转成文本上下文
   - 不发布 Session.Error
   - 保留原始 file part，继续作为“用户引用了这个文件路径”的语义进入消息流

这一顺序必须固定，避免把 PDF 提前归入“其他二进制文件”，导致现有附件能力退化。

### 后端主改动点：`packages/opencode/src/session/prompt.ts`

当前问题发生在 `createUserMessage` 的 `resolvePart` 逻辑里。`file://` 文件引用在进入该分支后，会根据 `part.mime` 和目标路径继续分流，但现有实现对“其他二进制文件”的处理过于激进，导致它们仍可能走到 Read 或触发错误。

本次在这里增加更明确的文件类型判定：

- 目录：沿用现有目录读取逻辑
- PDF / 图片：沿用现有 attachment 逻辑
- 文本文件：沿用现有 Read 逻辑
- 其他二进制文件：直接返回原始 `part`

对于最后一类，不再额外生成“Called the Read tool...”这类 synthetic text，也不再从二进制内容构造 data URL attachment。模型只看到：用户明确引用了某个文件路径。

### 保持前端协议不变

本次不修改以下前端逻辑：

- `packages/opencode/webgui/src/components/mention/MentionNode.tsx`
- `packages/opencode/webgui/src/components/MessageInput/hooks/useMessageParts.ts`
- `packages/opencode/webgui/src/components/MessageInput/...` 中与插入 `@路径`、拖拽路径、行号编码相关的逻辑

原因是这些模块当前职责清晰：

- 前端负责表达“用户引用了哪个路径、是否附带行号范围”
- 后端负责决定“这个引用要不要被展开成内容”

把修复限制在后端可以避免影响 WebGUI 的输入体验、IDE bridge 注入路径、拖拽路径引用等既有行为。

### 文本文件行号范围兼容性

`@foo.ts:3-12` 这类引用当前通过 URL 查询参数把范围信息传入后端，后端再交给 Read 工具按范围读取。

本次方案不会改变这条链路：

- 只要目标仍被识别为文本文件，就继续使用范围参数
- 因此文本文件的单文件引用、范围引用、symbol/file mention 语义都保持不变

若用户给真正的二进制文件写了 `:3-12`，新逻辑会忽略其“展开内容”的企图，只保留路径引用本身。这是合理降级，因为二进制文件没有可稳定复用的文本行号语义。

### PDF 与图片兼容性

PDF 需要保持现有“作为附件交给模型”的能力，因此必须在“其他二进制文件”之前被识别并短路处理。

换言之，本次不是简单地把“二进制文件”整体禁掉，而是把它细分为：

- **受支持媒体附件**：PDF / 图片，继续上传给模型
- **不支持展开的其他二进制**：仅保留路径引用

这样可以同时满足：

- `@manual.pdf` 继续可用
- `@plugin.vsix` 不再报错

### 最终消息语义

改动后，不同文件类型在模型上下文中的语义如下：

- **文本文件**：模型既知道路径，也会拿到展开后的文本内容
- **PDF / 图片**：模型会收到 attachment
- **其他二进制文件**：模型只知道用户引用了这个路径，不会拿到文件内容，也不会看到系统级报错

这与用户意图更一致：对于 `.vsix` 这类文件，通常只是想让模型围绕该文件路径、文件名或后续操作展开讨论，而不是直接解析其二进制内部内容。

## 风险与兼容性

### 风险

- 若文本 / 二进制判定边界不稳，可能误把可读文本文件降级成“仅路径引用”
- 若判断顺序错误，可能误伤 PDF，使其失去 attachment 能力
- 若直接删除 file part 而不是保留它，模型会丢失“用户引用了哪个文件”的路径上下文

### 降低风险的方式

- 复用现有后端媒体与二进制判定逻辑，避免新增一套分叉规则
- 固定判断顺序为：**目录 → PDF/图片 → 文本 → 其他二进制**
- 对文本范围引用、PDF、其他二进制各自加独立回归测试
- 对“其他二进制文件”采用保留原始 file part 的降级策略，而不是直接丢弃引用

## 非目标

本次不处理：

- 为 `.vsix`、`.zip` 等文件新增特殊 UI 徽标或文案
- 把“仅路径引用”再转换成单独的系统提示文本
- 扩展 WebGUI 上传白名单，让更多二进制文件走 attachment 上传
- 自动解析压缩包、安装包或数据库文件内部内容
- 重构整个 message part / mention 协议

## 预期结果

修复后，WebGUI 中的 `@文件` 引用会按用户意图更稳定地工作：

- `@foo.ts:3-12` 继续读取指定行范围
- `@manual.pdf` 继续作为附件交给模型
- `@plugin.vsix` 不再触发 `Cannot read binary file`，也不再弹出会话错误

最终用户会看到：真正支持展开的文件继续按原有方式工作；不支持展开的二进制文件则自动降级为“路径引用”，从而消除无意义的错误噪音，同时不破坏既有文本与 PDF 能力。

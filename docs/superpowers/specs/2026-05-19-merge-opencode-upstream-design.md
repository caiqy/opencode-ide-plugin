# 合并 opencode 上游更新设计

## 背景

当前仓库是 `opencode-ide-plugin` fork，既要持续跟进 `opencode` 上游更新，也要保留本 fork 在 IDE / WebGUI / host bridge / 发布流程上的本地适配。最近本地分支 `ide-plugin` 已积累一批 fork 专属改动，而上游远程 `opencode` 的默认分支是 `dev`。本次目标是在新分支 `chore/merge-upstream-20260519` 上按以往惯例合并 `opencode/dev`，并在冲突处尽量同时保留上下游功能。

## 目标

1. 将 `opencode/dev` 的最新更新合并到当前 fork 分支。
2. 对可安全判断的冲突，直接做“上下游兼容合并”，避免简单偏向一侧导致功能回退。
3. 对无法安全自动判断的冲突，整理成明确选项交由维护者决策。
4. 保持 merge 历史，便于后续继续同步上游。

## 非目标

- 不主动做与本次合并无关的重构。
- 不把 merge 改成 rebase 或重写历史。
- 不在缺乏证据时擅自删掉本 fork 的本地能力。
- 不承诺所有冲突都能一次性自动处理；高风险语义冲突需要人工确认。

## 方案选择

### 方案 A：直接 merge `opencode/dev`

优点：

- 最符合“按以往惯例合并上游更新”的语义。
- 保留真实 merge 历史，后续排查冲突来源更清晰。
- 对 fork 同步场景更稳妥。

缺点：

- 若上游跨度较大，冲突会集中出现。

### 方案 B：先分析差异热点，再执行 merge（推荐）

执行顺序：

1. `git fetch opencode`
2. 查看 `ide-plugin..opencode/dev` 的提交范围与差异热点
3. 在当前分支执行普通 `git merge opencode/dev`
4. 逐个处理冲突

优点：

- 最终仍是 merge，但在实际落地前先了解风险面。
- 更容易识别哪些文件是本 fork 高频改动区，需要优先保留本地语义。

缺点：

- 比直接 merge 多一步分析。

### 方案 C：rebase 到 `opencode/dev`

优点：

- 历史更线性。

缺点：

- 不符合本次“合并上游”的惯例。
- 对长期 fork 的上游同步风险更高。
- 更容易把历史冲突分散到大量提交中，增加处理成本。

## 选型结论

采用 **方案 B 的执行节奏**，最终动作仍然是 **merge `opencode/dev`**。

## 执行设计

### 分支与上游基线

- 当前工作分支：`chore/merge-upstream-20260519`
- fork 基线分支：`ide-plugin`
- 上游合并目标：`opencode/dev`

### 合并流程

1. 获取上游最新引用。
2. 分析当前 fork 与 `opencode/dev` 的提交差异与潜在热点文件。
3. 执行普通 merge。
4. 若无冲突，进入验证。
5. 若有冲突，按“冲突处理策略”分流。
6. 完成后运行最小必要验证，确认没有明显破坏核心能力。

### 冲突处理策略

#### 可直接处理的冲突

满足以下条件时，我会直接处理：

- 能明确看出一侧是格式、导入顺序、重命名或机械性改动，另一侧是功能改动。
- 上下游变更可通过合并代码结构同时保留，且不会引入明显重复逻辑。
- 本 fork 现有契约在仓库文档、近期 spec、测试命名或文件职责中有明确证据支持。
- 改动点属于桥接层、适配层、宿主封装层，本来就应承担“兼容上下游”的职责。

#### 需要你选择的冲突

出现以下情况时，我会停下来给你建议和选项：

- 上下游对同一行为给出了互斥语义，无法同时保留。
- 某段本地逻辑是否仍然需要保留，仓库中没有足够证据判断。
- 合并一侧会影响发布流程、版本规则、宿主兼容边界或长期维护策略。
- 涉及大范围架构迁移，简单拼接代码会留下高风险隐患。

### 决策原则

处理冲突时按以下优先级判断：

1. 尽量同时保留上游通用能力与本 fork 的 IDE / WebGUI 本地能力。
2. 优先保留已有测试、已有 spec、已有 repowiki/记忆文档支撑的本地契约。
3. 如果上游引入了更好的通用实现，优先让本地适配挂接到上游新结构上，而不是硬保留旧实现。
4. 若确实必须二选一，先暂停并让维护者决定。

## 数据流与影响面

本次不是新增功能，而是一次“上游代码流入 + 本地适配重挂”的集成工作。重点影响面预计包括：

- `packages/opencode/`：上游核心服务、工具、协议、配置入口
- `packages/opencode/webgui/`：本 fork 的 WebGUI 行为补丁与上游 UI 演进的交汇点
- `hosts/vscode-plugin/`：bridge、版本注入、宿主包装
- `hosts/jetbrains-plugin/`：宿主适配、版本/更新链路、本地 UI 封装
- 文档与构建配置：若上游调整目录、脚本或契约，可能需要跟进

## 错误处理与风险控制

- merge 前先 fetch 并看差异范围，减少盲合。
- 只对有把握的冲突做直接合并。
- 对高风险冲突保留现场并给出候选方案，不做猜测式修复。
- 合并后通过针对性命令做最小验证，优先覆盖受影响最大的模块。

## 验证策略

合并完成后，验证以“证明没有把核心本地能力直接合坏”为目标，按改动范围选择最小必要检查：

- `git status` 确认冲突已清理干净
- 针对受影响包执行类型检查 / 测试 / 构建
- 若冲突主要集中在 WebGUI 或宿主插件，则优先运行对应局部验证命令
- 若 merge 本身失败或验证暴露异常，再进入针对性排查

## 完成标准

当满足以下条件时，本次合并工作可视为完成：

1. `opencode/dev` 已成功 merge 到当前工作分支。
2. 所有 merge 冲突已解决。
3. 能自动判断的兼容冲突已处理完毕。
4. 不能自动判断的冲突已整理成清晰建议并经你确认。
5. 至少完成与受影响范围匹配的最小验证。

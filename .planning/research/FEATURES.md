# 功能全景：上游同步工作流

**领域:** 基于上游 CLI 工具构建的 IDE 插件项目的下游 Fork 管理
**研究日期:** 2026-04-12
**置信度:** 高（基于直接的代码库分析 + 成熟的 git/fork 管理模式）

## 背景

本项目是 `anomalyco/opencode` 的一个**深度分叉 Fork**——领先 384 个提交，640 个文件变更，新增 105K 行——下游新增内容分布在两个干净区域（`packages/opencode/webgui/` 和 `hosts/`），加上对上游文件的零散修改（SDK 生成、构建脚本、补丁、配置）。上游迭代迅速，有 200 多个活跃分支。

核心挑战：在每次合并后保持双方正常工作。目前不存在任何同步流程。

## 基础必备

用户期望的基础功能。缺失 = 同步流程崩溃或产生不可信的结果。

| 功能                           | 为什么是必需的                                                                                                                                                 | 复杂度 | 备注                                                                                                                                                                          |
| ------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **在专用分支上拉取并合并上游** | 没有专用同步分支，合并冲突会污染主开发分支。合并必须在隔离环境中进行。                                                                                         | 低     | 在 `sync/*` 分支上执行 `git fetch opencode && git merge opencode/dev`。标准 git 工作流。                                                                                      |
| **冲突检测报告**               | 合并后，开发者需要立即获得按风险区域分类的冲突文件列表（仅上游、仅下游、双方修改）。否则冲突只能随机发现。                                                     | 中     | 合并后执行 `git diff --name-only --diff-filter=U` + 按路径前缀分类（`packages/opencode/src/` = 上游核心，`webgui/` = 下游，`hosts/` = 下游，等等）。                          |
| **合并后构建验证**             | 能够编译通过的合并是最低标准。"构建通过"是 PROJECT.md 的字面核心要求。必须验证：bun typecheck、webgui build、vscode plugin compile、jetbrains plugin compile。 | 中     | 4 个独立的构建系统：bun（monorepo）、vite（webgui）、pnpm+tsc（vscode）、gradle（jetbrains）。每个都可能独立失败。                                                            |
| **SDK 重新生成检查**           | WebGUI 依赖从上游 OpenAPI 规范生成的 `@opencode-ai/sdk`。如果上游更改了 API 路由，SDK 就会过时。根据 CONCERNS.md，这是合并后故障的第一大来源。                 | 中     | 检测 `packages/opencode/src/server/routes/` 或 `packages/sdk/openapi.json` 的变更，触发 `./packages/sdk/js/script/build.ts`，然后检查 `sdkClient.ts` 的手动包装是否仍然对齐。 |
| **补丁兼容性检查**             | 存在 4 个依赖补丁，可能在上游依赖更新时失效。如果补丁在合并后无法应用，bun install 会失败且什么都无法构建。                                                    | 低     | `bun install` 在补丁不适用时会明确报错。但错误信息很晦涩——需要清晰的诊断。                                                                                                    |
| **测试套件运行**               | 现有测试（webgui 的 vitest、vscode 的 mocha）必须在合并后通过。测试是"功能不退化"的信号。                                                                      | 低     | 在 `packages/opencode` 中运行 `bun test`，在 `webgui/` 中运行 vitest，在 `hosts/vscode-plugin/` 中运行 mocha。                                                                |
| **回滚路径**                   | 如果同步合并有问题，开发者必须能够干净地中止或回退，而不损坏工作分支。                                                                                         | 低     | Git 已经提供了这个能力（`git merge --abort`、`git reset --hard`），但工作流必须记录/强制使用同步分支来保护开发分支。                                                          |

## 差异化功能

使同步更容易、更安全或更快的功能。非必需，但高价值。

| 功能                 | 价值主张                                                                                                                                                                                                            | 复杂度 | 备注                                                                                                                                                        |
| -------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **按区域影响分析**   | 将上游变更分类为风险区域："安全"（仅上游目录如 `packages/app/`、`infra/`、`docs/`）vs "有风险"（共享目录如 `packages/opencode/src/server/`、`packages/opencode/src/config/`）。开发者可以集中注意力在高风险变更上。 | 中     | 基于文件路径的分类。区域：仅上游（下游未触及）、仅下游（webgui、hosts）、共享（server 路由、config、bus 事件、package.json）。                              |
| **API 变更检测**     | 自动 diff 上游的 server 路由文件、Hono 路由定义和 bus 事件定义，以识别影响 WebGUI 的 API 契约变更。标记新增/更改/删除的端点。                                                                                       | 高     | 解析 `src/server/instance.ts` 和 `src/server/routes/*.ts` 中的路由注册，比较合并前后。也检查 `src/bus/` 中的 `BusEvent.define()` 调用以发现 SSE 事件变更。  |
| **配置模式变更检测** | 检测 `packages/opencode/src/config/config.ts` 的变更可能破坏 WebGUI 设置面板（使用 `any` 类型且没有编译时安全性）。                                                                                                 | 中     | Diff 配置模块，标记新增/删除/重命名的字段。至关重要，因为 CONCERNS.md 指出 `any` 类型意味着配置变更会导致静默的运行时故障。                                 |
| **依赖漂移报告**     | 合并后，比较根 `package.json` catalog 版本与下游期望的版本。标记 TypeScript 版本不匹配（根：5.8.2，webgui：5.9.3，vscode：5.0.0）。标记新增/删除的工作区包。                                                        | 中     | 解析 package.json 文件，比较版本。已是已知关注点（双包管理器、TS 版本不匹配）。                                                                             |
| **上游功能对等跟踪** | 跟踪哪些上游 SolidJS TUI 功能已在 React WebGUI 中重新实现，哪些缺失。当上游添加新的 TUI 功能时，标记为可能需要重新实现。                                                                                            | 高     | 需要维护 `packages/app/`（SolidJS）和 `packages/opencode/webgui/`（React）之间的功能映射。半手动过程。                                                      |
| **合并策略建议器**   | 对每个冲突文件，建议合并策略："采用上游"（仅上游关注的内容）、"采用我们的"（仅下游功能）、"需要手动合并"（双方都有合理的变更）。                                                                                    | 高     | 基于启发式：如果文件在 `hosts/` → 始终采用我们的。如果文件在 `packages/app/` → 始终采用上游。如果文件在 `packages/opencode/src/server/routes/` → 手动合并。 |
| **合并前预演**       | 在实际合并前，模拟合并以展示哪些文件会冲突，而不修改工作树。允许开发者在承诺合并前做好准备。                                                                                                                        | 低     | `git merge --no-commit --no-ff opencode/dev` 然后 `git diff --cached`，然后 `git merge --abort`。标准 git 操作，只需脚本化。                                |
| **变更日志提取**     | 拉取自上次同步以来的上游提交消息，按类别分组（feat、fix、refactor、breaking）。开发者一目了然地了解变更内容，而无需阅读 100 多个提交。                                                                              | 中     | `git log --oneline last-sync-tag..opencode/dev` 配合 conventional commit 解析。                                                                             |
| **同步频率跟踪**     | 记录每次同步的时间、吸收了多少上游提交、以及发生了多少冲突。检测同步频率是否在下降（间隔越长 = 合并越困难）。                                                                                                       | 低     | 简单的元数据文件（`.planning/sync-history.json`），在每次成功同步后更新。                                                                                   |

## 反特性（明确不做）

明确不应构建的功能。这些看似有用但会制造更多问题。

| 反特性                         | 为什么避免                                                                                                                               | 应该怎么做                                                                                                   |
| ------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------ |
| **自动冲突解决**               | 下游有 105K 行变更，自动化冲突解决会静默引入 bug。WebGUI 中的 `any` 类型意味着类型错误无法捕获不正确的合并。                             | 保持手动合并解决。提供分类和建议，但每个冲突需要人工决策。                                                   |
| **Cherry-pick 工作流**         | 逐个 cherry-pick 上游提交（而非合并）会创建一个随时间进一步分叉的平行历史。使未来的合并逐步变得更加困难。每次 cherry-pick 都是合并债务。 | 使用从上游分支顶端的完整合并。接受偶尔的大型合并而非积累 cherry-pick 债务。                                  |
| **Rebase 到上游**              | 将 384 个下游提交 rebase 到上游会重写历史、破坏现有 PR，并需要强制推送。下游历史包含合并提交和协作历史，不应被重写。                     | 仅使用基于合并的同步。保留下游历史原样。                                                                     |
| **自动化 sdkClient.ts 补丁**   | `sdkClient.ts` 中手写的 fetch 包装器（566 行）很脆弱且使用 `any` 类型。在 SDK 重新生成后尝试自动补丁会产生微妙的 bug。                   | 在 SDK 重新生成后标记手动包装器需要审查。长期目标：将所有手动包装器迁移到生成的 SDK（该文件中已有此 TODO）。 |
| **双向同步（向上游推送变更）** | 本项目有中文 UI 字符串、使用 React 而非 SolidJS、以及 IDE 特定扩展。几乎没有什么可以直接上推。尝试向上游提 PR 增加了开销而没有收益。     | 仅单向同步：上游 → 下游。如果上游需要下游发现的 bug 修复，作为独立 PR 直接贡献，而非通过同步流程。           |
| **用 Git submodule 管理上游**  | Submodule 可以隔离上游代码，但本项目修改了上游文件（补丁、SDK 脚本、构建配置）。Submodule 不支持这种用法——它们适用于只读依赖。           | 保持作为带远程跟踪的 Fork。当前的 `opencode` remote 设置是正确的。                                           |
| **自动化定时同步（CI cron）**  | 按计划自动合并会在冲突出现时创建损坏的分支，且没有人工了解变更内容的上下文。上游迭代太快，触及的文件太多，不适合无人值守的合并。         | 手动触发 + 人工监督。在上游有值得吸收的变更时同步，而非按定时器。                                            |

## 功能依赖关系

```
Pre-merge dry run ─────────────┐
                               v
Upstream fetch + merge ──> Conflict detection report
         │                     │
         v                     v
    Patch compat check    Impact analysis by zone
         │                     │
         v                     v
    SDK regen check       API change detection
         │                Config schema change detection
         v                     │
    Build verification <───────┘
         │
         v
    Test suite run
         │
         v
    Changelog extraction (optional, can run anytime)
         │
         v
    Sync frequency tracking (post-merge metadata)
```

关键依赖链：

- **拉取 → 合并 → 检测 → 构建 → 测试** 是关键路径
- **影响分析、API 检测、配置检测** 可以在冲突检测后并行运行
- **SDK 重新生成** 必须在构建验证之前完成（过时的 SDK = 构建失败）
- **补丁检查** 必须在构建验证之前完成（补丁失败 = 安装失败）
- **合并前预演** 是可选的，在实际合并之前运行
- **变更日志 + 频率跟踪** 是合并后的簿记工作

## MVP 推荐

### 第一阶段：核心同步循环（基础必备）

优先实现这些——它们构成最小可行同步工作流：

1. **在同步分支上拉取并合并上游** — 基础。没有这个，其他一切都没有意义。
2. **冲突检测报告** — 给开发者即时的态势感知。
3. **SDK 重新生成检查** — 根据 CONCERNS.md 的合并后第一大故障模式。
4. **补丁兼容性检查** — 第二大合并后故障模式。
5. **构建验证** — 验收门控（"构建通过"是核心价值宣言）。
6. **测试套件运行** — 回归门控。
7. **回滚路径** — 安全网。

这是一个脚本/清单，不是工具。保持简单。

### 第二阶段：智能层（差异化功能）

延后实现——这些改善体验但不构成阻塞：

- **按区域影响分析** — 最有价值的差异化功能。低投入，高回报。
- **合并前预演** — 让开发者在承诺前侦察。构建成本极低。
- **变更日志提取** — 有助于理解上游做了什么。
- **同步频率跟踪** — 简单的元数据，为流程纪律提供依据。

### 第三阶段：深度分析（愿景性）

在感受到痛点后再实现：

- **API 变更检测** — 高复杂度，对 sdkClient.ts 问题有很高价值。
- **配置模式变更检测** — 中复杂度，防止静默的运行时故障。
- **合并策略建议器** — 高复杂度，在合并冲突频繁时价值最大。
- **依赖漂移报告** — 中复杂度，防止 TS/依赖版本不匹配。
- **上游功能对等跟踪** — 持续的维护负担。
